Configuration

Systematic works out of the box with sensible defaults. This page covers every way to customize its behavior.

Config File Locations

Section titled “Config File Locations”

Systematic looks for configuration in three places, checked in this order (highest priority first):

  1. Custom config directory: $OPENCODE_CONFIG_DIR/systematic.{json,jsonc}
  2. Project-specific: .opencode/systematic.{json,jsonc}
  3. Global: ~/.config/opencode/systematic.{json,jsonc}

When both .jsonc and .json exist in the same directory, .jsonc takes precedence and .json is silently ignored. This lets you add comments to your config without renaming the existing file.

Trust Boundaries

Section titled “Trust Boundaries”

Fields that control provider routing or capability policy — model, variant, permission, and skills — are accepted only from user config (~/.config/opencode/systematic.json) or $OPENCODE_CONFIG_DIR/systematic.json. Project config may tune non-sensitive fields such as temperature, top_p, mode, color, steps, hidden, or exact-agent disable, but it cannot choose model/provider routing or loosen permission/capability policy.

A typo in agents.<key>, disabled_agents, or disabled_skills fails loudly with a clear error that names the offending key — no silent misconfiguration.

Workflow Guard

Section titled “Workflow Guard”

The workflow guard records privacy-safe receipts for supported engineering operations and surfaces whether guarded workflow requirements are satisfied. It covers local implementation and verification work, commits, pushes, and GitHub pull-request, check, and review readback when the required Git and GitHub environment is available.

The guard ships in observe mode by default. It records and reports workflow state without blocking operations. Protected mode is opt-in; it can reject a guarded transition when required evidence is missing or stale. Disabled mode turns the guard off for the configured scope.

workflow_guard is trust-protected. Set it in user configuration (~/.config/opencode/systematic.json) or $OPENCODE_CONFIG_DIR/systematic.json; project-level .opencode/systematic.json cannot set this field.

Agent and Category Overlays

Section titled “Agent and Category Overlays”

Use top-level agents and categories maps to tune bundled Systematic agents without copying their markdown files into native OpenCode agent definitions.

Overlay application precedence for a Systematic-owned bundled agent (strongest first):

  1. Exact agents.<key> overlay (high-trust model wins)
  2. categories.<category-id> overlay (high-trust model wins)
  3. Bundled markdown/frontmatter defaults (model-free)
  4. OpenCode inherited defaults

Bundled agents inherit the invoking model unless high-trust user or $OPENCODE_CONFIG_DIR/systematic.json config supplies an explicit model. Set "model": null to clear an explicit model and restore parent-model inheritance. Project config cannot set, erase, or shadow model at any value.

A flat agents.<name>.model now also routes in-process Pi delegates, not just OpenCode — previously it applied to OpenCode only.

Profiles and Per-Harness Routing

Section titled “Profiles and Per-Harness Routing”

For a task-oriented walkthrough, see the model profiles guide. A profile is a named, reusable bundle of routing overrides — model, variant, temperature, top_p, and the opencode/pi blocks below — defined once in your user config’s profiles map and selected by name. Profiles exist for people who work across repositories that warrant different model routing from the same harness: define work and personal profiles once in user config, then let each repository pick one.

Any config source may set the top-level profile selector to choose among the user’s profiles — including a repository’s project config:

Only profile (the selector) is project-settable. profiles (the map of bundle definitions) is trust-protected exactly like model, variant, permission, and skills — a project may choose among the profiles you’ve defined, but it cannot define new ones or see into ones you haven’t shared. A profiles map set in project config is ignored with a warning. Both your user config and $OPENCODE_CONFIG_DIR config (“custom” config) may define a profiles map; a name is looked up in custom’s map first, then user’s, so a bundle defined only in custom config is still selectable by any source.

profile is tri-state: leaving it unset means “no opinion, let a lower-priority source decide”; setting it to a name selects that bundle; setting it to null explicitly means “base configuration, no profile” and wins outright over a weaker source’s name — this is how a repository can opt out of your default profile rather than merely failing to set one. The strongest source that sets profile at all wins: custom config, then project config, then user config.

If the selected name doesn’t match a defined profile (in either custom’s or user’s profiles map), Systematic warns once and falls back to your own profile default (if you have one and it resolves — checked the same way, custom first, then user); if that’s also undefined, it falls back to base configuration with no profile active. Run systematic config show to see the active profile, which source selected it, and any fallback that occurred.

Switching which profile is active never changes an agent’s visibility, permissions, mode, or existence: unlike an ordinary same-key overlay override (which fully replaces the previous value), the active profile’s overlay merges field-by-field over the base config — a field the profile bundle is schema-incapable of carrying (mode, color, steps, hidden, disable, permission, skills) simply survives untouched regardless of which profile is selected. ProfileOverlaySchema restricts a profile entry to routing-only fields for exactly this reason.

Per-harness routing blocks

Section titled “Per-harness routing blocks”

agents.<name> and categories.<category> overlays accept optional opencode and pi blocks so one config routes correctly on both harnesses, while the existing flat model/variant fields stay as the harness-neutral default:

Resolution precedence, evaluated independently for model and for the harness’s qualifier (variant on OpenCode, thinking on Pi): agent block > agent flat > category block > category flat. Merge order across sources is user base → selected profile → project → custom, with each later source overriding the same field at the same level.

model: null is a value, not an absence — it means “inherit from the parent session” and beats a lower layer’s explicit model at the same precedence level. But it obeys the same precedence as any other value: a block’s null beats a flat explicit model at the same level, not the other way around. Concretely, a profile that sets agents.x.model: null does not undo a base config’s agents.x.opencode.model — the block is more specific than the flat field it’s trying to override, so OpenCode keeps the block’s model. To restore inheritance on OpenCode specifically, set agents.x.opencode.model: null. When model: null wins at layer L on OpenCode, any variant is dropped too — inheriting the parent’s model means inheriting its variant as well; there is no “inherited model, explicit variant” combination.

The two harnesses’ qualifiers bind to model differently. OpenCode’s variant is coupled to whichever layer supplies model: let L be the most specific layer (agent block > agent flat > category block > category flat) that sets model. variant is used only from L or a MORE specific layer than L — a variant from a LESS specific layer is dropped, so a more specific layer’s model change doesn’t accidentally inherit a stale variant from further up the merge chain:

Setting variant with no model resolving anywhere for that agent on OpenCode — after every layer is merged — is a config-load error naming the agent and opencode. A profile is allowed to set opencode.variant alone precisely because the model is expected to come from a lower layer (your base config); the error only fires when no layer supplies one on OpenCode.

Pi’s thinking qualifier, by contrast, is independent of model: it applies to whatever model the Pi delegate ends up running, including a model inherited from the parent session when no layer sets one at all. pi.thinking with no model resolving anywhere is a normal, valid configuration — never a config-load error. This mirrors how the deprecated pi_subagents.thinking field always behaved.

pi_subagents.<name>.thinking is deprecated

Section titled “pi_subagents.<name>.thinking is deprecated”

The legacy pi_subagents.<name>.thinking field (and its category form) is superseded by agents.<name>.pi.thinking / categories.<category>.pi.thinking. The new location wins when both are set; the legacy field is honored only when the new location is unset, and using it prints one deprecation warning naming the exact legacy field you wrote — a category-level pi_subagents.categories.<category>.thinking write prints one warning naming that category, not one per agent in it. Migrate by moving thinking into the pi block.

Schema and Autocomplete

Section titled “Schema and Autocomplete”

Add a $schema field to your systematic.json to enable per-key autocomplete in editors that honor JSON Schema property completion:

VS Code is the reference target — it picks up $schema automatically and provides inline completion, hover documentation, and validation squiggles. Zed, IntelliJ, and other editors that support JSON Schema property completion will also benefit, though support varies by editor version.

Typed Validation

Section titled “Typed Validation”

Since v2.15.0, Systematic validates agents.<key>, disabled_agents, and disabled_skills against the actual set of bundled names at load time. A typo fails loudly with a clear error that names the offending key. The valid bundled names are listed in the error when validation fails, so the error message is the fix.

If your config contains a typo in any of these fields, Systematic will fail to load on upgrade and surface the error. The fix is to correct the key to a valid bundled name.
