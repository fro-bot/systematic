Configuration

Systematic works out of the box with sensible defaults. This page covers every way to customize its behavior.

Config File Locations

Section titled “Config File Locations”

Systematic reads up to five config files. A later file in this table overrides an earlier one:

OrderLayerFile
1user~/.config/opencode/systematic.{jsonc,json}
2user.local~/.config/opencode/systematic.local.{jsonc,json}
3project<repository root>/.systematic.{jsonc,json}, else <repository root>/.opencode/systematic.{jsonc,json}
4custom$OPENCODE_CONFIG_DIR/systematic.{jsonc,json}
5custom.local$OPENCODE_CONFIG_DIR/systematic.local.{jsonc,json}

The custom layers exist only when OPENCODE_CONFIG_DIR is set and not blank. Every file is optional.

Systematic picks a file by whether it exists, never by whether it is valid:

  • When both .jsonc and .json exist in the same directory, .jsonc takes precedence and .json is ignored. This lets you add comments to your config without renaming the existing file.
  • In a repository, a root file (.systematic.jsonc, else .systematic.json) takes precedence over a file under .opencode/. Systematic never merges the two. It ignores the .opencode/ file and warns once, naming both paths.
  • A file that is chosen but invalid is never skipped in favor of another file. Systematic reports the chosen file as invalid.
  • A file exists when its directory entry exists. A symlink whose target is gone counts: Systematic chooses it, reports it as unreadable and does not fall back to another file.

The layer names user.local and custom.local are the ones that appear in prose and in systematic config show. The JSON output of config show spells them userLocal and customLocal.

Every config file is JSONC. Comments and trailing commas are accepted in objects and arrays, in all five files, so a file that Prettier or your editor formats loads as it is.

The repository root

Section titled “The repository root”

Systematic reads the project file from the repository root. The root is the nearest ancestor of the start directory that holds a .git entry (a .git file counts, so a linked worktree works). Systematic resolves a root it finds with realpath, so a symlinked checkout shows its real path in warnings and in config show. If no ancestor holds a .git entry, the start directory itself is the root and stays as given.

The start directory depends on the surface:

SurfaceStart directory
OpenCode v1The directory OpenCode gives the plugin
OpenCode v2The location directory of the session. With no project directory, only the user-level files load.
PiThe working directory of the Pi process at startup. Pi loads config once, so a project file you add later is read after a restart.
systematic commandThe current directory (systematic search takes --dir)

So a session in packages/app/ of a monorepo reads the project file at the repository root, not one inside packages/app/. A nested repository with its own .git is its own root and reads only its own project file.

The lookup is by .git alone. A home directory that is itself a git repository becomes the root for every directory below it that has no repository of its own.

When a session starts in a subfolder that has its own .opencode/systematic.* file and the root is a different directory, Systematic does not read that file. It warns once, naming the file and the project config path it reads instead.

Local overlay files

Section titled “Local overlay files”

systematic.local.jsonc (or systematic.local.json) sits beside a user-level file: beside ~/.config/opencode/systematic.jsonc, and beside the file in OPENCODE_CONFIG_DIR. It is a second file for settings that belong to one machine, such as absolute source roots, projects and the allow list, so the main file can live in your dotfiles. Systematic never creates or gitignores the local file for you.

  • A local file has the trust of the file it sits beside. It may set every field that file may set, and search.enabled and search.allow_project_sources included.
  • It needs no sibling. A local file with no systematic.jsonc beside it is valid.
  • It overrides the file beside it and every earlier layer in the table. The project file and the custom layers still override it. An agents or categories entry in a local file replaces the entry with the same key from earlier layers whole, the way a custom entry does. It does not merge field by field.
  • A source in search.sources that has the same name as a source in an earlier user-level file replaces that source whole, including its projects and its exclude list.
  • An invalid local file is named in the error. OpenCode v1, OpenCode v2 and Pi fail at startup and name the local file. The systematic command and the systematic-search command report it and carry on with the files that are valid. See When a config file is invalid.
  • systematic config show reports the origin of a routing value from a local file as the kind of the file beside it (user or custom).

If OPENCODE_CONFIG_DIR points at your user config directory (spelled the same way or through a symlink), Systematic reads each file once. It applies each file at both positions, so the shared file still outranks the project file. No warning is shown.

When a config file is invalid

Section titled “When a config file is invalid”

The five files are not equally trusted, so a failure costs different amounts:

  • A broken user, user.local, custom or custom.local file is fatal. OpenCode v1, OpenCode v2 and Pi fail at startup and name the file. These are your own files, so Systematic does not hide the mistake.
  • A broken project file is skipped. The project file comes from a repository, so a pull, a branch or a contributor’s formatter must not be able to take your plugin down. Systematic leaves out the whole file, loads with the other layers, and warns once per process. The warning names the file and the reason: the JSONC error code and offset, the reason a read failed, or the schema path of the first field that failed validation. It never shows a value or any of the file’s text, and it never shows a key you chose: a map key, such as a name under categories or profiles, appears as <key>, and an unrecognized key is reported by the section it sits under. The other warnings the same file would have produced are dropped, so the skip warning is the only one for that file.
  • A project file fails when it cannot be read, is larger than 1 MB, is not valid JSONC, has a root that is not an object, or has a top-level field that fails validation. It also fails when it loads alone but breaks the load once merged with the other layers, for example a project profile bundle you opted into that names an unknown category. Systematic retries the load without the project file. If the retry succeeds, the project file is skipped. If it fails too, the original error stands.
  • An empty or whitespace-only project file is the same as no file. There is no warning.
  • A bad search field or source in a project file is dropped on its own, with its own warning. It never causes the whole file to be skipped.
  • A project file that is also your custom file stays fatal. Systematic reads such a file once, through the custom layer, which is strict.
  • Exporting pi-subagents at project scope stops on a broken project file. The export writes into the repository, so it refuses to run on a partial view of the config. It writes nothing.

systematic config show marks a skipped project file with the reason, in the Resolved configuration section, and exits 0. With --json, a skipped file adds a projectSkipped object with path and reason; the key is absent otherwise.

Seeing which files are in play

Section titled “Seeing which files are in play”

systematic config show lists the paths it resolved: the user, user.local and project files, plus the custom and custom.local files when OPENCODE_CONFIG_DIR is set, and the .opencode/ file that a root project file shadows. A local file’s path is listed even when the file does not exist. With --json, these are the locations keys user, userLocal, project, custom, customLocal and ignoredProject. custom and customLocal are null without a custom directory, and ignoredProject is null unless a root file shadows an .opencode/ file. The command prints the project and user files, and never prints the text of a local file. It prints the project file’s text only when the file’s real path is inside the repository root: a project file that is a symlink to a file outside the repository, or whose target cannot be resolved, gets a one-line note (is not shown: it resolves outside the repository or it could not be resolved) that never names the target. It strips terminal escape sequences and control characters, other than newlines and tabs, from the project file’s text. Your own user file prints as written, so a symlink from your dotfiles still works. It reads those two files with the same 1 MB cap as the project config. A file that is larger, is not a regular file (a directory or a named pipe) or cannot be read gets a one-line note instead of its text, and the rest of the output still prints.

config show also has a Search section for the current project, and --json carries it under search. It stays available when the configuration fails to load. See See what search will do.

systematic config path prints the resolved user and project paths.

Migrating

Section titled “Migrating”

The repository root rule changes four things for existing setups:

  • A subfolder .opencode/systematic.* file is no longer read. Earlier releases read .opencode/systematic.json from the directory the session started in, so a monorepo package could carry its own. Now only the root’s project file is read, unless the subfolder has a .git of its own. Move the file to the repository root:

    A file at <repository root>/.opencode/systematic.json keeps working. Until you move the subfolder file, each load warns once and names both paths.

  • A git-managed home directory becomes the root for the directories below it that have no repository of their own. A project directory below it that held its own .opencode/systematic.json is no longer its own root. Run git init in that project to make it one, or move the file to the home directory’s root if you want it to apply to all of them.

  • A found root is resolved with realpath. A symlinked checkout shows its real path in warnings and in config show.

  • A project config file over 1 MB is not loaded. The search readers always had this cap. Now the full loader applies it too. OpenCode v1, OpenCode v2 and Pi skip the file with one warning that names it, and load with the other layers. The systematic command and the systematic-search command report it and carry on. The cap applies to the project file only. Trim the file, or move bulk content out of it.

Trust Boundaries

Section titled “Trust Boundaries”

Fields that control provider routing or capability policy — model, variant, permission, and skills — are accepted only from user config (~/.config/opencode/systematic.json) or $OPENCODE_CONFIG_DIR/systematic.json, or from the systematic.local.json file beside either, which has the same trust. Project config, whether it is .systematic.json at the repository root or .opencode/systematic.json, may tune non-sensitive fields such as temperature, top_p, mode, color, steps, hidden, or exact-agent disable, but it cannot choose model/provider routing or loosen permission/capability policy.

A typo in agents.<key>, disabled_agents, or disabled_skills fails loudly with a clear error that names the offending key — no silent misconfiguration.

Removed Settings

Section titled “Removed Settings”

The workflow_guard setting has been removed along with the workflow guard it configured. A workflow_guard key is still accepted in every config file (user, $OPENCODE_CONFIG_DIR, and project), with any value, so a config written for an earlier release keeps loading. The key has no effect.

Each config file that carries the key logs one warning per load. The warning names the file and the key, never prints the value, and links to this section. Delete the key from that file to silence it.

The guard was off by default, so a configuration that never set workflow_guard behaves as it did before. If you had turned on observe, the receipts, status tools, and guidance it produced are gone. If you had turned on protected, it no longer blocks guarded commits, pushes, pull-request creation, or completions.

Agent and Category Overlays

Section titled “Agent and Category Overlays”

Use top-level agents and categories maps to tune bundled Systematic agents without copying their markdown files into native OpenCode agent definitions.

Overlay application precedence for a Systematic-owned bundled agent (strongest first):

  1. Exact agents.<key> overlay (high-trust model wins)
  2. categories.<category-id> overlay (high-trust model wins)
  3. Bundled markdown/frontmatter defaults (model-free)
  4. OpenCode inherited defaults

Bundled agents inherit the invoking model unless high-trust user or $OPENCODE_CONFIG_DIR/systematic.json config supplies an explicit model. Set "model": null to clear an explicit model and restore parent-model inheritance. Project config cannot set, erase, or shadow model at any value.

A flat agents.<name>.model now also routes in-process Pi delegates, not just OpenCode — previously it applied to OpenCode only.

Skill Permissions on OpenCode v1

Section titled “Skill Permissions on OpenCode v1”

OpenCode v1 has two tools that load a skill: the native skill tool and the systematic_skill tool. They ask for permission under different names. The native tool asks with the bare name, such as git-worktree. systematic_skill asks with the prefixed name, such as systematic:git-worktree. A permission rule only reaches the tool whose name form it uses.

Systematic writes both forms where it writes the rules itself:

  • skills list on an agent or category. The list denies every skill and then allows each one you name. Each allow is written for both name forms, so the agent can load a listed skill with either tool. A skill whose name already contains a colon, such as ce:plan, has only one form.
  • disabled_skills. A disabled skill is hidden from systematic_skill and from the generated commands. OpenCode’s own skill discovery still scans the whole bundled skills folder, so Systematic also adds a top-level permission.skill deny for each disabled skill, in both name forms. The native tool then leaves the skill out of its list and refuses to load it. Your own top-level permission rules are kept. If you already wrote a rule for the same skill name, yours stays as it is. When you take a skill out of disabled_skills, the denies Systematic added are removed on the next load.

A managed skills list that names a disabled skill is rejected when the config loads, with an error that names the skill.

The systematic: allow that Systematic adds for a skills list is only a default. A rule you write yourself for the systematic: name always wins: if you wrote one, anywhere in your overlays, Systematic does not add its own for that skill. It also adds none when a rule you wrote for the bare name is the one that takes effect.

Rules you write yourself in permission.skill are not copied to the other name form. To block a skill completely with a hand-written rule, write both forms:

OpenCode v2 uses one name form for both tools, so this only applies to v1.

Profiles and Per-Harness Routing

Section titled “Profiles and Per-Harness Routing”

For a task-oriented walkthrough, see the model profiles guide. A profile is a named, reusable bundle of routing overrides — model, variant, temperature, top_p, and the opencode/pi blocks below — defined once in your user config’s profiles map and selected by name. Profiles exist for people who work across repositories that warrant different model routing from the same harness: define work and personal profiles once in user config, then let each repository pick one.

Any config source may set the top-level profile selector to choose among the user’s profiles — including a repository’s project config:

Only profile (the selector) is project-settable by default. profiles (the map of bundle definitions) is trust-protected exactly like model, variant, permission, and skills — a project may choose among the profiles you’ve defined, but it cannot define new ones or see into ones you haven’t shared, unless you opt in (see below). A profiles map set in project config is ignored with a warning unless the opt-in is on. Both your user config and $OPENCODE_CONFIG_DIR config (“custom” config), and the systematic.local file beside each, may define a profiles map; a name is looked up in custom.local’s map first, then custom’s, then user.local’s, then user’s, so a bundle defined only in custom config is still selectable by any source. A bundle defined in a local file sits in the same slot of the merge chain as one defined in the file beside it, so the local file’s own overlay beats it.

Opting a repository into defining its own profiles

Section titled “Opting a repository into defining its own profiles”

Setting allow_project_profiles: true in your user (or $OPENCODE_CONFIG_DIR) config lets a project systematic.json define its own profiles map and have it consulted for bundle content — useful when a repository wants to ship routing recommendations (e.g. “use this cheaper model for this repo’s review agents”) without you hand-copying them into your own config.

allow_project_profiles is user-owned only — exactly like profiles itself, a project config can never set this field; doing so is stripped before the project config is even parsed and produces the same “ignored” warning as any other project-trust field. A project cannot grant itself a permission it does not already have. The opt-in is resolved from your user and $OPENCODE_CONFIG_DIR config only (including the systematic.local file beside each), before the project config is loaded, so setting it in the SAME file as a profiles map does not work either — both are stripped together, as if neither had been written.

A project-defined bundle is advisory, not authoritative: it supplies routing only where your own config is silent for that field, and can never override a value you set — not even partially. If you set agents.correctness-reviewer.model yourself, a project bundle that also sets it has no effect on that agent’s model at all; the project’s value never applies and never appears anywhere in the resolved config. This is enforced structurally by where the project bundle sits in the merge chain (before your base config, not after) combined with field-by-field merging — not by a policy check that a future change could accidentally bypass. A repository whose entire suggested profile is already covered by your own config is a normal, silent no-op: systematic config show shows you exactly which fields, if any, actually came from the project (see the model profiles guide).

A project-defined profile name can never shadow one you or $OPENCODE_CONFIG_DIR config already defined: bundle lookup checks custom.local, custom, user.local, user, then project last. If your personal profile and a repository’s personal profile both exist, yours always wins the name. This protects a name you have defined content for — it does not protect a name you have only referenced. If your own profile default names a bundle you never defined (or typoed), that name is still looked up through the same custom-then-user-then-project order, so an opted-in repository’s own profiles entry of that same name is consulted and can supply content for it; the usual “not defined in profiles” warning does not fire, because the name IS defined — by the repository, not by you.

Because assertAllProfileBundlesAreValid validates every bundle in every source that may define one — including, once opted in, every bundle in a project’s profiles map — a malformed bundle anywhere in that map fails the merge even if nobody ever selects it. Systematic then skips the whole project file, with one warning, and loads with your own config (see When a config file is invalid). A malformed bundle in your own user or custom config still fails the load. Opting in makes your config depend on content you did not author, so a bad bundle in a repository costs you its suggestions.

The repository still decides which of its own (or your) profiles is active for itself, via its project config’s profile selector — same as today, opt-in or not. That is the point of a project selecting a profile, not a gap: a repository choosing to route itself through the work profile you already defined is exactly what profile selection is for. If you disagree with a repository’s selection for your own session, SYSTEMATIC_PROFILE=<name> in your shell environment outranks every config source’s profile value, including the project’s — set it to override, or to a nonexistent name to fall back to your own default.

profile is tri-state: leaving it unset means “no opinion, let a lower-priority source decide”; setting it to a name selects that bundle; setting it to null explicitly means “base configuration, no profile” and wins outright over a weaker source’s name — this is how a repository can opt out of your default profile rather than merely failing to set one. The strongest source that sets profile at all wins: custom config (custom.local over custom), then project config, then user config (user.local over user).

If the selected name doesn’t match a defined profile (in either custom’s or user’s profiles map), Systematic warns once and falls back to your own profile default (if you have one and it resolves — checked the same way, custom first, then user); if that’s also undefined, it falls back to base configuration with no profile active. Run systematic config show to see the active profile, which source selected it, and any fallback that occurred.

Switching which profile is active never changes an agent’s visibility, permissions, mode, or existence: unlike an ordinary same-key overlay override (which fully replaces the previous value), the active profile’s overlay merges field-by-field over the base config — a field the profile bundle is schema-incapable of carrying (mode, color, steps, hidden, disable, permission, skills) simply survives untouched regardless of which profile is selected. ProfileOverlaySchema restricts a profile entry to routing-only fields for exactly this reason.

Per-harness routing blocks

Section titled “Per-harness routing blocks”

agents.<name> and categories.<category> overlays accept optional opencode and pi blocks so one config routes correctly on both harnesses, while the existing flat model/variant fields stay as the harness-neutral default:

Resolution precedence, evaluated independently for model and for the harness’s qualifier (variant on OpenCode, thinking on Pi): agent block > agent flat > category block > category flat. Merge order across sources is user base → selected profile → user.local → project → custom → custom.local, with each later source overriding the same field at the same level — when the active profile came from your user or $OPENCODE_CONFIG_DIR config. When the active profile is a project-defined bundle (the opt-in above), it merges before user base instead, so your base config overrides it field by field rather than the other way around; see the opt-in section above for what that means in practice.

model: null is a value, not an absence — it means “inherit from the parent session” and beats a lower layer’s explicit model at the same precedence level. But it obeys the same precedence as any other value: a block’s null beats a flat explicit model at the same level, not the other way around. Concretely, a profile that sets agents.x.model: null does not undo a base config’s agents.x.opencode.model — the block is more specific than the flat field it’s trying to override, so OpenCode keeps the block’s model. To restore inheritance on OpenCode specifically, set agents.x.opencode.model: null. When model: null wins at layer L on OpenCode, any variant is dropped too — inheriting the parent’s model means inheriting its variant as well; there is no “inherited model, explicit variant” combination.

The two harnesses’ qualifiers bind to model differently. OpenCode’s variant is coupled to whichever layer supplies model: let L be the most specific layer (agent block > agent flat > category block > category flat) that sets model. variant is used only from L or a MORE specific layer than L — a variant from a LESS specific layer is dropped, so a more specific layer’s model change doesn’t accidentally inherit a stale variant from further up the merge chain:

Setting variant with no model resolving anywhere for that agent on OpenCode — after every layer is merged — is a config-load error naming the agent and opencode. A profile is allowed to set opencode.variant alone precisely because the model is expected to come from a lower layer (your base config); the error only fires when no layer supplies one on OpenCode.

Pi’s thinking qualifier, by contrast, is independent of model: it applies to whatever model the Pi delegate ends up running, including a model inherited from the parent session when no layer sets one at all. pi.thinking with no model resolving anywhere is a normal, valid configuration — never a config-load error. This mirrors how the deprecated pi_subagents.thinking field always behaved.

pi_subagents.<name>.thinking is deprecated

Section titled “pi_subagents.<name>.thinking is deprecated”

The legacy pi_subagents.<name>.thinking field (and its category form) is superseded by agents.<name>.pi.thinking / categories.<category>.pi.thinking. The new location wins when both are set; the legacy field is honored only when the new location is unset, and using it prints one deprecation warning naming the exact legacy field you wrote — a category-level pi_subagents.categories.<category>.thinking write prints one warning naming that category, not one per agent in it. Migrate by moving thinking into the pi block.

Typed Validation

Section titled “Typed Validation”

Since v2.15.0, Systematic validates agents.<key>, disabled_agents, and disabled_skills against the actual set of bundled names at load time. A typo fails loudly with a clear error that names the offending key. The valid bundled names are listed in the error when validation fails, so the error message is the fix.

If your user or custom config contains a typo in any of these fields, Systematic will fail to load on upgrade and surface the error. The fix is to correct the key to a valid bundled name. A typo in a project file does not stop the plugin: Systematic skips that file and warns, naming the field. See When a config file is invalid.
